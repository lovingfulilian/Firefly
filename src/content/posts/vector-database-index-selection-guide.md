假设知识库里有 100 万段文字。用户提问后，Embedding 模型会把问题变成一个向量，系统接下来要从这 100 万个向量中找出最相似的几个。

一种做法是把 100 万个向量全部比较一遍。这种方法结果准确，却可能太慢。另一种做法是提前整理数据，例如建立导航图或把相似向量分组，查询时只检查最有希望的一小部分。后者速度更快，但可能漏掉少量正确结果。

这就是向量索引要解决的问题：

> 在查询速度、召回质量和资源成本之间找到平衡。

本文不会一上来堆缩写和参数，而是按照下面的顺序展开：

```text
向量检索在做什么
→ 精确搜索与近似搜索怎样分类
→ 相似度怎样计算
→ 每种索引怎样工作
→ 每个参数代表什么
→ 不同业务怎样选
→ 如何在 Milvus 中落地
→ 线上出现问题怎样排查
```

读完后，你不需要记住所有参数值，但应该能够解释：为什么选择某种索引、准备调哪个参数，以及这个调整会付出什么代价。

## 一、开始之前：向量检索到底在做什么

### 1.1 向量是什么

Embedding 模型会把文本、图片或其他内容转换成一组数字，例如：

```text
“如何申请年假” → [0.12, -0.31, 0.08, ...]
“年假申请流程” → [0.11, -0.29, 0.09, ...]
```

这组数字就是向量。示例只写了 3 个数字，真实模型可能输出几百或几千个数字，这个数字个数叫作**向量维度**。

语义接近的内容，在向量空间中的位置通常也比较接近。向量检索就是先把用户问题转换成向量，再寻找距离最近或相似度最高的数据。

### 1.2 Top-K 是什么

`K` 表示希望返回多少条结果：

- `Top-1`：只返回最相似的 1 条；
- `Top-10`：返回最相似的 10 条；
- `Top-100`：返回最相似的 100 条。

K 越大，搜索和传输的数据通常越多，后续 Reranker（重排模型）的成本也越高。RAG 中常见的做法不是把 Top-K 设得无限大，而是先召回几十条候选，再重排出少量证据。

### 1.3 精确搜索与近似搜索

向量搜索可以先分为两大类：

```text
向量搜索
├─ 精确最近邻搜索
│  └─ FLAT：逐个比较全部候选
└─ 近似最近邻搜索（ANN）
   ├─ HNSW：建立近邻图
   ├─ IVF_FLAT：先聚类，再搜索部分分组
   ├─ IVF_PQ：先聚类，再用压缩向量计算
   └─ DiskANN 等：主要索引放在磁盘
```

ANN 是 **Approximate Nearest Neighbor** 的缩写，中文是“近似最近邻搜索”。它不是某一种具体索引，而是 HNSW、IVF 等近似索引的统称。

“近似”表示系统不再检查所有向量，因此可能漏掉少量真正的最近邻。换来的好处是查询更快，可以支撑更大的数据量和更高的并发。

### 1.4 Recall@K 是什么

怎样知道近似索引漏掉了多少结果？常用指标是 `Recall@K`，即 Top-K 召回率。

例如先用 FLAT 得到准确的 Top-10，再用 HNSW 查询同一个问题。如果 HNSW 找回了其中 9 条：

```text
Recall@10 = 9 / 10 = 90%
```

这里衡量的是“近似索引能否找到精确搜索的结果”，不是大模型最终回答是否正确。评估索引时至少要同时看两类指标：

- **质量：** Recall@K；
- **性能：** P50、P95、P99 查询延迟和 QPS。

P95 为 80 毫秒，表示 95% 的请求能在 80 毫秒内完成。QPS 表示系统每秒能处理多少次查询。

## 二、先确定“相似”的含义：三种常见度量

索引负责更快地找到邻居，相似度度量负责定义谁才是邻居。建索引和查询必须使用一致的度量。

### 2.1 余弦相似度：比较方向

余弦相似度主要比较两个向量的方向，不太关心向量本身有多长。

可以把两个向量想成两支箭：箭头方向越接近，余弦相似度越高。

**常见用途：** 文本语义检索、RAG 知识库，以及向量长度没有明确业务含义的场景。

```text
cosine(x, y) = (x · y) / (||x|| × ||y||)
```

不需要死记公式，只要知道它先计算两个向量的内积，再除以各自长度，使结果主要反映方向。

余弦相似度通常越大越相似，但有些数据库返回的是“余弦距离”，此时数值越小越相似。设置阈值前一定要看当前产品返回的是相似度还是距离。

### 2.2 内积：方向和长度都会影响结果

内积通常写作 `IP`，来自 Inner Product：

```text
inner_product(x, y) = x · y
```

它没有除以向量长度。因此除了方向，向量长度也可能影响得分。

**常见用途：** 模型文档明确推荐内积，或者向量长度本身包含置信度、热度等业务信号的推荐系统。

如果所有向量都做过 L2 归一化，也就是每个向量的长度都被调整为 1，那么内积和余弦相似度的排序相同。此时应根据模型说明和向量库的实测性能选择。

### 2.3 L2：比较空间中的直线距离

L2 也叫欧氏距离，表示两个点在空间中的直线距离。距离越小，两个向量越接近。

```text
L2(x, y) = sqrt(Σ(xᵢ - yᵢ)²)
```

**常见用途：** Embedding 模型明确按欧氏距离训练、图像特征或数值特征中绝对位置有意义的场景。

### 2.4 应该怎么选

| 情况 | 推荐起点 |
| --- | --- |
| Embedding 模型明确指定度量 | 严格遵循模型说明 |
| 普通文本语义检索，没有特殊说明 | 先试余弦相似度 |
| 模型输出已归一化，并推荐内积 | 使用内积 |
| 向量长度包含业务意义 | 验证内积 |
| 模型按欧氏空间训练 | 使用 L2 |

最重要的规则不是“文本永远用余弦”，而是下面三点：

1. 入库与查询使用同一个 Embedding 模型版本；
2. 入库向量和查询向量使用相同的归一化流程；
3. 建索引、查询和离线评估使用同一种度量。

## 三、第一类索引：FLAT 精确搜索

### 3.1 它怎样工作

FLAT 没有复杂的导航结构。查询到来时，它会把查询向量与候选向量逐个比较，然后按距离排序。

```text
查询向量
├─ 与向量 1 比较
├─ 与向量 2 比较
├─ 与向量 3 比较
└─ ……直到比较完全部候选
```

它类似于在没有目录的书架上逐本检查。速度未必快，但不会因为索引近似而漏掉真正的最近邻。

### 3.2 优缺点

**优点：**

- 结果精确；
- 不需要训练或维护复杂索引；
- 数据更新后可以直接参与搜索；
- 可以作为其他索引的评估基线。

**缺点：**

- 数据越多，需要比较的向量越多；
- 高维向量、高并发和较大 Top-K 会进一步增加计算量。

### 3.3 什么时候选择

- 数据量较小；
- 先通过租户、权限或分类过滤，剩余候选很少；
- 对结果精确性要求高于查询速度；
- 正在为 HNSW 或 IVF 制作准确的 Top-K 对照结果。

不要把“超过十万条就不能用 FLAT”当成固定标准。100 万条数据如果先过滤到 500 条，精确扫描这 500 条可能比使用复杂近似索引更合适。最终边界要靠真实延迟测试决定。

## 四、第二类索引：IVF_FLAT 先分组再搜索

### 4.1 它怎样工作

IVF 是 **Inverted File Index** 的缩写，可以理解为“把相近向量分到同一个区域”。

建索引时，IVF 使用聚类算法把全部向量分成多个列表，每个列表都有一个中心点：

```text
全部向量
├─ 列表 1：报销、发票、费用……
├─ 列表 2：请假、考勤、年假……
├─ 列表 3：账号、密码、登录……
└─ ……
```

这里的文字只是帮助理解。真正分组依据是向量距离，并不知道业务分类名称。

查询时，系统先判断查询向量靠近哪些列表中心，然后只扫描这些列表中的向量，不再检查全部数据。

`IVF_FLAT` 后面的 FLAT 表示：向量在每个列表中仍以原始精度保存。它只是减少了要搜索的列表，没有压缩向量。

### 4.2 两个核心参数

#### nlist：一共分成多少个列表

`nlist` 中的 `n` 可以理解为 number，`list` 就是列表。因此 `nlist=1024` 表示把向量空间分成 1024 个列表。

- `nlist` 太小：每个列表装的数据很多，查询仍要扫描大量向量；
- `nlist` 太大：每个列表数据太少，训练和管理成本上升，也更容易因为选错列表而漏召回。

#### nprobe：一次查询检查多少个列表

`probe` 表示探测。`nprobe=16` 表示一次查询选择 16 个最接近的列表进行搜索。

- `nprobe` 越小：搜索更快，但可能漏掉相邻列表里的正确结果；
- `nprobe` 越大：召回通常更高，但延迟也会增加；
- 当 `nprobe` 接近 `nlist` 时，几乎所有列表都被搜索，IVF 的加速优势也就很小了。

可以先记住这个关系：

```text
nlist 决定建索引时怎样分区
nprobe 决定每次查询搜索多少个分区
```

### 4.3 什么时候选择

- 数据量较大，希望减少搜索范围；
- HNSW 的内存占用或建索引成本不能接受；
- 数据主要是批量导入，分布相对稳定；
- 可以通过调整 `nprobe` 在速度和召回之间取舍。

### 4.4 常见问题

IVF 需要根据已有数据训练聚类中心。如果只有很少数据就创建索引，分组通常不可靠。大量新数据持续加入、Embedding 模型更换或业务数据分布明显改变后，原有分组也可能不再适合，需要重新评估或重建索引。

## 五、第三类索引：HNSW 用近邻图导航

### 5.1 它怎样工作

HNSW 全称是 **Hierarchical Navigable Small World**，中文常译为“分层可导航小世界图”。名字很长，核心可以拆成两点：

1. 相似向量之间建立连接，形成一张近邻图；
2. 图分为多层，上层节点少、适合快速跳转，下层节点多、适合精细查找。

查询过程类似导航：先在高速公路上快速接近目标区域，再进入普通道路，最后在附近寻找最接近的节点。

```text
稀疏上层：快速跨区域移动
      ↓
中间层：缩小搜索范围
      ↓
密集底层：寻找最终近邻
```

### 5.2 三个核心参数

#### M：每个节点最多建立多少条连接

`M` 控制图的连接密度。例如 `M=16`，可以简单理解为每个节点最多保留约 16 个重要邻居连接。具体实现细节会因产品而不同。

- `M` 较大：道路更多，不容易走进死路，召回通常更好；
- 代价：图占用更多内存，建索引更慢，写入成本更高。

#### efConstruction：建图时愿意比较多少个候选邻居

`efConstruction` 只在建索引阶段使用。它表示插入一个节点时，算法会保留多大的候选集合，从中挑选合适的邻居。

- 数值较大：建出来的图通常质量更高；
- 代价：构建更慢，需要更多 CPU 和临时资源。

它不会直接决定每次线上查询要搜索多少节点。

#### ef 或 efSearch：查询时保留多少个候选节点

不同向量库可能叫 `ef` 或 `efSearch`。它控制一次查询愿意探索多大的候选集合。

- 数值较小：查询更快，召回可能下降；
- 数值较大：搜索更充分，召回通常提高，但延迟和 CPU 消耗增加。

三个参数的分工可以归纳为：

| 参数 | 生效阶段 | 控制什么 | 调大后的主要代价 |
| --- | --- | --- | --- |
| `M` | 建索引 | 图中每个节点的连接数量 | 内存、构建和写入成本增加 |
| `efConstruction` | 建索引 | 构图时考虑的候选邻居数量 | 构建时间增加 |
| `ef` / `efSearch` | 查询 | 查询时探索的候选节点数量 | 查询延迟和 CPU 增加 |

### 5.3 什么时候选择

- 在线 RAG 或语义搜索重视低延迟和较高召回；
- 数据和图索引能够放进内存；
- 数据规模在单机或集群内仍可管理；
- 查询频率高于大批量持续写入频率。

如果没有明确限制，HNSW 通常是常规在线向量检索值得优先测试的索引。但它不是无条件最优：内存紧张、大量更新或强过滤场景都需要单独验证。

## 六、第四类索引：IVF_PQ 用压缩换空间

### 6.1 它与 IVF_FLAT 有什么区别

IVF_PQ 前半部分仍然是 IVF：先把向量分成多个列表。不同之处在于，列表里的向量不再全部使用原始浮点数计算，而是经过 PQ 压缩。

PQ 全称是 **Product Quantization**，中文是“乘积量化”。它会把一个高维向量切成多个小段，为每一段找到一个较短的编码。

可以把它理解成把详细地址压缩成区域编码：存储更省空间，比较更快，但编码无法保留原始地址的全部细节。

### 6.2 常见参数

#### m：把向量切成多少个子向量

例如一个 768 维向量设置 `m=96`，可以理解为拆成 96 段，每段处理 8 个维度。许多实现要求向量维度能够被 `m` 整除，具体限制应查看向量库文档。

#### nbits：每个子向量编码使用多少 bit

`nbits` 控制每段编码能表示多少种情况。常见起点是 8 bit，但并非所有产品和数据都适合相同值。

- 编码更短：更省内存，但量化误差更大；
- 编码更长：保留的信息更多，但空间优势变小。

IVF_PQ 还会继续使用前面讲过的 `nlist` 和 `nprobe`：前者控制分多少组，后者控制查多少组。

### 6.3 什么时候选择

- 数据达到数千万甚至更大规模；
- 原始向量或 HNSW 图难以全部放入内存；
- 业务可以接受少量召回或排序损失；
- 可以保留原始向量，对初步候选执行精确重排。

一个常见落地方式是：

```text
IVF_PQ 快速召回 100 条候选
→ 读取这 100 条的原始向量
→ 使用相同度量重新精确计算
→ 返回最终 Top-10
```

这叫两阶段检索。第一阶段节省资源，第二阶段减少量化误差对最终排序的影响。

## 七、磁盘型索引什么时候才需要

DiskANN 一类索引把主要数据结构放在 SSD，而不是要求全部常驻内存。它适合数据规模远超内存、读多写少、SSD 性能稳定的场景。

它不是入门项目的默认选择，因为还要处理磁盘吞吐、缓存预热、并发和尾延迟。如果 HNSW 或 IVF 已经满足规模与成本，就没有必要为了使用更复杂的算法而切换磁盘型索引。

## 八、索引应该怎么选

### 8.1 先看五个条件

不要只问“有多少条向量”。选型前至少要记录：

1. **数据规模和维度：** 有多少向量，每个向量多少维；
2. **质量目标：** Recall@10 最低要达到多少；
3. **性能目标：** P95、P99 延迟和并发要求；
4. **资源预算：** 可用内存、CPU 和磁盘；
5. **数据特征：** 更新是否频繁，查询是否带租户、权限等过滤。

### 8.2 从这张表开始

| 场景 | 推荐起点 | 原因 |
| --- | --- | --- |
| 数据量小，或过滤后只剩少量数据 | FLAT | 精确、简单，不需要维护 ANN 索引 |
| 常规在线 RAG，重视速度和召回 | HNSW | 速度与召回的平衡通常较好 |
| 数据较大，HNSW 内存压力明显 | IVF_FLAT | 不保存近邻图，可通过搜索列表数控制成本 |
| 数据很大，原始向量内存压力也明显 | IVF_PQ + 精排 | 通过压缩减少空间，用精排补偿误差 |
| 数据远超内存且读多写少 | 磁盘型索引 | 使用 SSD 承载主要索引 |
| 需要评估其他索引是否漏结果 | FLAT | 生成精确 Top-K 作为基线 |

### 8.3 一个简单决策流程

```text
过滤后候选是否很少？
├─ 是 → 先测试 FLAT
└─ 否
   ├─ 索引能否放进内存？
   │  ├─ 能 → 优先测试 HNSW
   │  └─ 不能 → 测试 IVF_FLAT 或 IVF_PQ
   └─ 数据是否远超内存且主要为读取？
      └─ 是 → 再评估磁盘型索引
```

“推荐起点”不是最终答案。最后必须使用同一批真实查询，比较 Recall@K、P95/P99、QPS、内存、索引大小和构建时间。

## 九、Milvus 落地：为知识库建立 HNSW 索引

假设现在有一个企业知识库：

- 约 300 万个文本块；
- 向量维度为 1024；
- 使用余弦相似度；
- 每次返回 Top-10；
- 数据可以放进内存；
- 以在线查询为主，每天批量更新。

这种场景可以从 HNSW 开始。

### 9.1 创建索引

```python
from pymilvus import MilvusClient

client = MilvusClient(uri="http://localhost:19530")

# 准备索引配置
index_params = MilvusClient.prepare_index_params()
index_params.add_index(
    field_name="embedding",          # 存放向量的字段
    index_name="embedding_hnsw",     # 索引名称，方便后续管理
    index_type="HNSW",               # 使用 HNSW 近似索引
    metric_type="COSINE",            # 使用余弦相似度
    params={
        "M": 16,                     # 每个节点保留的最大连接数
        "efConstruction": 200,       # 建图时考虑的候选邻居数量
    },
)

client.create_index(
    collection_name="knowledge_chunks",
    index_params=index_params,
)
```

`M=16` 和 `efConstruction=200` 只是测试起点。它们适不适合当前项目，需要通过 Recall@K、构建时间和内存实测判断。

### 9.2 带业务过滤进行查询

```python
results = client.search(
    collection_name="knowledge_chunks",
    anns_field="embedding",          # 在哪个向量字段中搜索
    data=[query_embedding],           # 用户问题生成的查询向量
    limit=10,                         # 返回 Top-10
    filter='tenant_id == "acme" and status == "active"',
    search_params={
        "metric_type": "COSINE",    # 必须与建索引时保持一致
        "params": {
            "ef": 80,                # 查询时最多探索多大的候选集合
        },
    },
    output_fields=["document_id", "chunk_id", "title"],
)
```

这里的 `filter` 表示只返回 `acme` 租户中状态为有效的数据。权限条件必须由检索层执行，不能把无权内容交给大模型后再要求它不要回答。

### 9.3 参数怎样调

准备 500～2000 条具有代表性的真实查询，然后按以下顺序测试：

1. 使用 FLAT 生成每条查询的准确 Top-10；
2. 固定 `M=16`、`efConstruction=200` 建第一版 HNSW；
3. 分别测试 `ef=32、64、80、128、256`；
4. 记录 Recall@10、P95、P99、QPS 和 CPU；
5. 选择能够达到召回目标的最小 `ef`；
6. 如果增大 `ef` 仍不能达到目标，再检查索引构建质量、数据和度量。

先调查询参数 `ef`，因为它不需要重建索引。只有确定查询阶段无法满足目标时，再修改 `M` 或 `efConstruction` 并重建。

Milvus 不同版本支持的索引和参数可能变化，落地前应核对当前版本的[索引选型说明](https://milvus.io/docs/index-explained.md)和 [IVF_FLAT 文档](https://milvus.io/docs/ivf-flat.md)。

## 十、一个关键细节：过滤为什么会导致结果不足

生产查询通常包含租户、权限、语言、状态或时间过滤。假设库中只有 1% 的数据属于当前用户：

```text
ANN 先找出 100 条相似结果
→ 应用权限过滤
→ 平均只剩 1 条
→ 无法返回要求的 Top-10
```

此时 Embedding 和索引本身可能都没有问题，真正的问题是 ANN 候选集在过滤后太小。

不同向量库可能采用以下方式：

- 先过滤，再进行向量搜索；
- 先进行 ANN 搜索，再过滤结果；
- 搜索和过滤交替执行，不足时继续扩大搜索范围。

处理方法要根据过滤选择性决定：

| 情况 | 可考虑的方案 |
| --- | --- |
| 过滤后候选只有几百条 | 对过滤结果直接执行 FLAT |
| 少量固定大租户或大分类 | 按租户或分类分区、分片 |
| 高频过滤字段 | 给标量字段建立合适索引 |
| ANN 后过滤导致 Top-K 不足 | 扩大候选集或使用迭代扫描 |
| 权限过滤 | 在检索层强制执行，并纳入离线评估 |

pgvector 也明确说明了近似索引与过滤组合时可能返回不足，并提供 iterative scan 扩大扫描范围，详情可参考其[官方 Filtering 文档](https://github.com/pgvector/pgvector#filtering)。

## 十一、线上故障排查：先定位在哪一层

线上检索变差时，不要一开始就调 `ef` 或重建索引。向量检索链路可以分为五层：

```text
原始内容与切块
→ Embedding 与向量处理
→ 相似度与索引
→ 过滤与查询参数
→ 系统资源与服务状态
```

排查也应按这个顺序缩小范围。

### 11.1 第一步：先描述清楚故障现象

先确认属于哪一种问题：

- **结果不相关：** 返回了 Top-K，但内容不对；
- **结果数量不足：** 要 10 条，只返回几条；
- **延迟升高：** 结果正确，但 P95/P99 变慢；
- **结果不稳定：** 相同查询在不同时间差异很大；
- **资源异常：** 内存、CPU、磁盘或索引构建成本过高。

同时确认影响范围：所有查询、特定租户、特定过滤条件，还是模型升级后的新数据。

### 11.2 第二步：用 FLAT 区分“数据问题”和“索引问题”

对少量故障查询关闭 ANN，使用 FLAT 精确搜索：

- FLAT 结果也不相关：优先检查切块、Embedding、模型版本和相似度；
- FLAT 正确而 ANN 错误：重点检查索引参数、索引状态和过滤执行；
- 两者结果都正确但线上回答错误：问题可能在 Reranker、上下文组装或生成阶段。

这是最有效的分界线。没有 FLAT 对照时，很容易把 Embedding 问题误判为 HNSW 参数问题。

### 11.3 第三步：检查数据和 Embedding

按顺序检查：

1. 查询与入库是否使用同一个模型和版本；
2. 两边是否使用相同的文本预处理与归一化；
3. 向量维度是否正确，是否出现零向量、空值或 NaN；
4. 文档切块是否把标题、条件或答案拆散；
5. 新旧 Embedding 是否混在同一个索引中。

Embedding 模型升级时应保存 `embedding_model` 和 `embedding_version`，使用新字段或新集合重建，不要让不同向量空间的数据相互比较。

### 11.4 第四步：检查度量和索引参数

如果 FLAT 正确而 ANN 召回下降，再检查：

- 建索引和查询是否使用同一种度量；
- HNSW 的 `ef` 是否过小；
- HNSW 构建时的 `M`、`efConstruction` 是否过低；
- IVF 的 `nprobe` 是否过小；
- IVF 是否在数据太少时训练；
- 数据分布改变后，IVF 是否需要重新训练；
- PQ 压缩是否造成过大的排序误差，是否需要原向量精排。

每次只改变一个主要参数，并保存测试结果。否则即使效果变好，也无法判断是哪项调整起作用。

### 11.5 第五步：检查过滤与 Top-K

如果只在特定租户或权限条件下结果不足：

1. 记录过滤前后候选数量；
2. 检查过滤是发生在 ANN 之前还是之后；
3. 暂时扩大 ANN 候选或开启迭代扫描，观察结果是否恢复；
4. 比较过滤后 FLAT 与 ANN 的 Recall@K；
5. 判断是否需要分区、标量索引或对小候选集改用 FLAT。

不要仅在无过滤查询上做离线评估。真实过滤条件必须成为测试集的一部分。

### 11.6 第六步：检查资源和服务状态

如果结果正确但延迟升高，检查：

- 索引是否已完整加载；
- 是否刚启动，缓存仍未预热；
- CPU 是否被索引构建、批量写入或压缩任务占满；
- HNSW 图和原始向量是否超过内存，引发换页；
- 磁盘型索引的 SSD 延迟和吞吐是否异常；
- 请求并发、Top-K、`ef` 或 `nprobe` 是否被调大；
- 网络传输和 `output_fields` 是否返回了过多内容。

平均延迟无法反映长尾问题，应同时查看 P50、P95 和 P99，并分别测试冷缓存、热缓存、低过滤命中率和目标并发。

## 十二、常见问题速查

| 现象 | 优先检查 | 常见处理 |
| --- | --- | --- |
| ANN 结果比 FLAT 差 | `ef`、`nprobe`、度量、索引质量 | 增大查询范围；必要时重建索引 |
| 只返回少量结果 | 过滤选择性、候选集大小、空向量 | 扩大候选、迭代扫描、小集合改用 FLAT |
| HNSW 内存过高 | 向量维度、数据量、`M`、副本数 | 降低 `M`、半精度、IVF、量化或磁盘方案 |
| IVF 召回逐渐下降 | 数据漂移、列表分布、训练样本 | 使用新数据重新评估和训练 |
| 更新后搜到旧内容 | 主键、版本字段、删除标记 | 使用稳定 ID，过滤有效版本，后台清理 |
| 相似度阈值失效 | 模型版本、归一化、得分定义 | 用当前模型的正负样本重新标定 |
| P99 突然升高 | 缓存、资源竞争、参数和过滤 | 预热索引、隔离构建任务、限制查询预算 |

## 十三、一套最小可用的评估流程

1. 收集 500～2000 条真实查询，保留租户和权限条件；
2. 固定数据版本、Embedding 模型、归一化和相似度度量；
3. 使用 FLAT 生成准确 Top-K；
4. 对 HNSW 或 IVF 测试多组查询参数；
5. 记录 Recall@K、P95、P99、QPS、内存和索引大小；
6. 在目标并发下重复测试，而不是只做单线程测试；
7. 用人工标注或业务指标继续评估最终检索质量；
8. 保存每次测试的参数和环境，让结论可以复现。

可以先设定服务目标：

```text
Recall@10 ≥ 95%
P95 ≤ 80 ms
P99 ≤ 150 ms
内存不超过单副本预算
```

然后选择满足全部目标、总体成本最低的配置。没有必要为了把 Recall@10 从 98% 提高到 98.2%，让 P99 和机器成本翻倍。

## 十四、总结

现在可以把整篇文章压缩成四组知识：

### 搜索分类

- FLAT 是精确搜索，会比较全部候选；
- ANN 是近似搜索的统称，HNSW、IVF 都属于 ANN。

### 索引分类

- HNSW 用近邻图导航，适合常规在线低延迟检索；
- IVF_FLAT 先聚类，再搜索部分列表；
- IVF_PQ 在 IVF 基础上压缩向量，适合内存受限的大规模数据；
- 磁盘型索引用 SSD 换取更大的容量。

### 参数分类

- HNSW：`M` 控制图的连接数，`efConstruction` 控制建图质量，`ef` 控制查询范围；
- IVF：`nlist` 控制分多少组，`nprobe` 控制查多少组；
- PQ：`m` 控制切成多少段，`nbits` 控制每段编码精度。

### 选型原则

- 小数据或过滤后候选很少，先测试 FLAT；
- 常规在线检索，先测试 HNSW；
- HNSW 内存压力大，再测试 IVF_FLAT；
- 原始向量也放不下，再考虑 IVF_PQ 或磁盘型索引；
- 所有近似索引都要与 FLAT 比较 Recall@K；
- 真实过滤条件必须进入评估和排障流程。

索引选型不是背诵一个“百万级用 HNSW、千万级用 IVF”的固定答案。数据维度、过滤比例、并发、更新方式和硬件都会改变结果。真正可靠的方法，是先建立精确基线，再用真实查询找到能够同时满足召回、延迟和资源预算的配置。
